# 3.8.2 System Design

HealthTrack was designed as a role-based healthcare management system that supports patient service access, queue management, clinical documentation, workflow monitoring, follow-up scheduling, reporting, and offline operation. The system is composed of two user-facing web applications and a backend API service:

1. **HealthTrack PatientSide** – a patient-facing portal for registration, service selection, queue joining, service-status monitoring, medical-record viewing, follow-ups, and profile management.
2. **HealthTrack WEB** – a staff-facing console for queue operations, patient records, clinical consultation, service processing, inventory, reports, workflow monitoring, and heat-map analysis.
3. **HealthTrack API** – a Laravel-based backend-for-frontend API responsible for authentication sessions, password reset, verification, account administration, notifications, AI requests, and heat-map data access.
4. **Supabase Data Layer** – provides PostgreSQL database services, authentication, row-level security, real-time updates, storage, and service-specific data tables.
5. **Offline Support Layer** – uses Dexie IndexedDB and synchronization services to allow selected queueing and clinical operations to continue during temporary connectivity loss.

## A. System Architecture Model

HealthTrack follows a layered architecture:

- **Presentation Layer** – React and Vite applications for patient and staff interfaces.
- **Application Layer** – reusable components, route protection, role-based navigation, workflow services, queue services, and offline synchronization.
- **API and Authentication Layer** – Laravel API using Sanctum session cookies and Supabase JWT session bridging.
- **Data Layer** – Supabase PostgreSQL tables, database functions, row-level security policies, real-time subscriptions, and storage buckets.
- **Local Persistence Layer** – IndexedDB through Dexie for offline queues, cached patient data, pending records, documents, and synchronization jobs.

The architecture separates the user interfaces from backend services while allowing both portals to use a common source of truth for patients, queues, service requests, records, and workflow statuses.

## B. User and Role Model

The system uses role-based access control to ensure that each user can access only the modules appropriate to their responsibilities.

| User Role | Main Responsibilities | Major Modules |
|---|---|---|
| Patient | Register, select services, join queue, monitor requests, view records, and manage profile | Patient Portal, Service Intake, My Queue, Service Status, Medical Records, Follow-ups |
| Doctor | Conduct consultations, record diagnoses, prescribe treatment, approve clinical documents, and review cases | Doctor Consult, Patient Records, Queue, Follow-ups, Reports, Heat Map |
| Nurse | Manage queue operations, process service requests, encode patient information, manage inventory, and complete workflows | Queue, Service Desk, Patient Records, Inventory, Workflow, Archive, Reports |
| BHW | Encode patients who arrive at the facility and issue queue numbers | Encode Desk |
| Volunteer | Assist with patient encoding and queue registration | Encode Desk |
| Authorized Account Manager | Manage approved staff and patient account access | Accounts |

Access is enforced through protected frontend routes, role-based navigation, backend portal-session validation, Supabase authentication, and row-level security policies.

## C. Process and Workflow Model

The main process begins when a patient registers or logs into the Patient Portal. The patient selects a health service and submits the required intake information. A service request is created and associated with the selected patient and service type.

The general process is as follows:

1. Patient registration or authentication
2. Service selection
3. Service intake and requirement submission
4. Creation of a service request
5. Queue registration or appointment association
6. Queue number issuance
7. Nurse or BHW processing
8. Doctor consultation, when required
9. Diagnosis, prescription, document preparation, or service completion
10. Follow-up schedule creation, when applicable
11. Patient notification and status updates
12. Completion, release, archiving, or reporting

Each service may use a different workflow template. For example, an outpatient consultation may include registration, vital signs, consultation, diagnosis and prescription, and completion. Animal-bite services may include registration, queue assignment, nurse assessment, vaccination, and follow-up scheduling.

The workflow model is represented using:

- `service_requests` for the main patient-service transaction
- `service_request_steps` for individual workflow steps
- `workflow_logs` for the audit trail of status transitions
- `queue` for patient waiting and service progression
- `appointments` for scheduled visits
- `patient_records` for clinical and consultation information

## D. Data Model

The major data entities are organized around the patient-service transaction.

| Entity | Purpose |
|---|---|
| `profiles` | Stores authenticated staff profiles and assigned roles |
| `patients` | Stores patient identity, demographic, contact, and ownership information |
| `appointments` | Stores scheduled patient visits and appointment status |
| `service_types` | Defines available RHU services, queue prefixes, and workflow templates |
| `service_requests` | Represents a patient request for a particular service |
| `service_request_steps` | Stores the progress of each step in a service workflow |
| `workflow_logs` | Records workflow actions and status changes |
| `queue` | Stores queue numbers, patient status, service codes, and counter information |
| `patient_records` | Stores demographics, vital signs, diagnoses, notes, and clinical information |
| `certificates` | Stores medical certificates, health cards, death certificate reviews, and related releases |
| `permits` | Stores sanitary, exhumation, cremation, and transfer permit requests |
| `tb_monitoring` | Stores tuberculosis treatment schedules and follow-up information |
| `animal_bite_doses` | Stores anti-rabies vaccination schedules and dose monitoring |
| `inventory` | Stores medicines, supplies, quantities, and stock movement |
| `estimated_cases` | Stores community-reported cases used in the heat-map module |
| `email_logs` | Stores notification history for patient communication |
| `requirements_submissions` | Stores uploaded requirements and supporting documents |

The main entity relationships are:

- One patient can have many appointments.
- One patient can have many service requests.
- One service request belongs to one service type.
- One service request may be linked to one appointment and one queue ticket.
- One service request may contain multiple workflow steps.
- One patient may have multiple patient records and follow-up schedules.
- One patient record may be associated with a queue entry, appointment, and service request.
- Workflow logs belong to a service request and record actions performed by staff.

## E. Queue and Status Model

The queue module uses a state-based model to represent the progress of a patient visit.

Typical queue states include:

- `waiting`
- `next`
- `called`
- `in_progress`
- `skipped`
- `completed`
- `done`
- `cancelled`

These states are used by both staff and patients. Staff members can update the queue status, while patients can view the current status of their own queue ticket. The system can also trigger email or SMS notifications when important status transitions occur.

## G. Offline and Synchronization Model

HealthTrack includes an offline-capable design for essential RHU operations. When the connection is unavailable, selected information is stored locally using Dexie IndexedDB. Pending operations are placed in a local synchronization queue.

The synchronization process follows these steps:

1. Detect network availability.
2. Store new or updated queue and record data locally.
3. Mark local records as pending synchronization.
4. Retry synchronization when the connection returns.
5. Submit pending changes to Supabase.
6. Mark successful records as synchronized.
7. Refresh the local cache with the latest remote data.

This design reduces disruption during unstable internet connectivity while maintaining the central Supabase database as the authoritative source of data.

## H. Security and Access Model

Security is implemented through several controls:

- Sanctum-based HTTP-only session cookies for portal authentication
- Supabase JWT session integration
- Role-protected frontend routes
- Portal-specific access validation
- Supabase row-level security policies
- Patient ownership checks
- Staff-only access to clinical and administrative modules
- Throttling for login, password reset, verification, AI, notification, and heat-map requests
- Audit logging for selected user and workflow actions
- Controlled access to uploaded documents and patient records

This design ensures that patients can access only their own information, while staff members can access operational data according to their assigned role.

## I. System Design Summary

The HealthTrack system design integrates patient-facing services, staff operations, queue management, clinical workflows, records management, reporting, notifications, and offline synchronization in one healthcare information system. Its modular and role-based architecture supports different RHU responsibilities while maintaining consistent data relationships, controlled access, traceable workflows, and reliable patient-service interactions.

## 4.2.4 Database Structure

HealthTrack uses a relational database structure centered on the patient-service lifecycle. The database is organized to support patient information, service requests, queue management, clinical workflows, document generation, follow-up tracking, and system auditing. In the implemented design, the database is primarily managed through Supabase PostgreSQL, while local browser storage is used temporarily for offline operations.

### Core Database Design

The central data model is built around these primary entities:

- `profiles` – stores authenticated staff user information, assigned roles, and account metadata.
- `patients` – stores patient identity, demographics, contact information, and ownership/consent-related data.
- `service_types` – defines the healthcare services offered by the RHU, including queue prefix, workflow templates, and service metadata.
- `appointments` – stores scheduled or follow-up visits for patients.
- `service_requests` – represents the main transaction where a patient requests a particular health service.
- `service_request_steps` – tracks progress for each step in the service workflow.
- `workflow_logs` – records timestamps, actor identity, status transitions, and workflow event history.
- `queue` – stores queue numbers, current status, assigned counters, and processing state.
- `patient_records` – maintains completed clinical encounters, diagnoses, treatment notes, and patient history.
- `certificates` – stores generated medical certificates and related release records.
- `permits` – stores permit requests such as sanitary, exhumation, cremation, and transfer permits.
- `tb_monitoring` – documents tuberculosis-related monitoring schedules and treatment follow-up information.
- `animal_bite_doses` – stores rabies vaccine schedules and dose completion tracking.
- `inventory` – tracks medicines, medical supplies, stock quantities, and stock movement.
- `estimated_cases` – stores community-reported cases for heat-map and reporting analysis.
- `email_logs` – records sent notifications and communication history.
- `requirements_submissions` – stores uploaded patient requirements and supporting documents.

### Relationship Model

The database structure follows common relational patterns to maintain consistency and traceability:

- One patient can have many appointments.
- One patient can have many service requests.
- One service request belongs to one service type.
- One service request may be linked to one appointment and one queue record.
- One service request can have many workflow steps.
- One patient may have many patient records and follow-up records.
- One patient record may reference one queue entry, one appointment, and one service request.
- One service request may produce many workflow logs.
- One workflow log belongs to a single service request and is associated with a user action or status update.

These relationships allow the system to maintain a complete historical record of patient care from intake to diagnosis, follow-up, and final processing.

### Queue and Workflow Tables

The queue and workflow structure is a key element of the system. The `queue` table holds the current waiting-line state, while `service_requests` defines the actual patient transaction. The `service_request_steps` table decomposes a service into manageable workflow states such as registration, assessment, consultation, diagnosis, document creation, and completion. This makes it possible to track progress at a granular level and supports both operational monitoring and patient status updates.

The `workflow_logs` table complements this structure by providing an auditable history of every change. It records who performed an action, when it happened, which workflow step was updated, and what status was recorded. This is essential for compliance, supervision, and issue investigation.

### Data Security and Integrity

The database design supports secure data handling by combining relational integrity with application-level access controls. Supabase Row-Level Security (RLS) ensures that users only access data appropriate to their role and ownership. Clinical and administrative tables are protected so that patients can only view their own records, while authorized staff can access operational data according to assigned permissions.

The design also emphasizes data integrity through foreign-key style relationships, workflow validation, and audit history. This reduces duplicate records, ensures that each service request is properly associated with a patient and queue entry, and creates a reliable record of healthcare activity.

### Local Offline Database Structure

For offline scenarios, the frontend applications use IndexedDB through Dexie. This local storage layer holds pending queue transactions, cached patient and service record data, and synchronization metadata. Its purpose is not to replace the central database but to temporarily support critical operations when the network is unavailable.

The offline structure generally includes:

- queue entries waiting to sync
- pending patient service updates
- cached patient information for quick view
- unsynced workflow events
- synchronization status flags to mark records as pending or completed

Once internet access is restored, the application pushes the pending local updates to Supabase and marks them as synchronized.

### Database Structure Summary

The HealthTrack database model is structured around a patient-centered healthcare transaction flow. Each service request, queue instance, workflow step, and clinical record is designed to be traceable, role-protected, and synchronized with the broader system. This structure supports rapid queue management, clinical documentation, reporting, offline resilience, and secure data governance across the entire HealthTrack platform.
